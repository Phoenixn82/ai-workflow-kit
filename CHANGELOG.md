### Security fixes (3.0.0, review rounds 1 to 5, S1-S16, R2-1, R2-2, R3-1 to R3-4, R4-1, R5-1)

- **Security (installer):** uptime-kuma and ntfy listen on 127.0.0.1 only under host networking (macOS and Windows publish them on 127.0.0.1), and the installer starts them, and Pi-hole, only once `server-lane-heimdall` and its firewall are in place, also with `--only` and after a failed setup; share them with `tailscale serve` (S4). Every piped bootstrap (uv, mise, Tailscale, Ollama) is downloaded to a private folder, checked against a pinned sha256 and only then run; npm, pip, uv, mise and image names carry exact versions, FreeLLMAPI is pinned to a commit and installed with `npm ci`, and the manifest check refuses floating installs, `pip3 install` and `npm i -g` included (S10). Hook commands are rendered with the home path quoted for where it stands, so a home with spaces, quotes, `$` or backslashes works and a launch guard is kept; the installer adds `bypassPermissions` and `skipDangerousModePermissionPrompt` only when the safety dispatcher's PreToolUse hook is wired (S12). Settings are written through a unique `mkstemp` file at the final mode, never a predictable temp name (S15). freellmapi-bootstrap keeps a differing unit as `.bak-<time>` before replacing it (S13).
- **Security (servers):** Linux firewall changes are a trial every time: running rules only, rolled back after 5 minutes (or a restart) unless confirmed from a NEW SSH session with `setup.sh --confirm-firewall`; a confirm from an already-open session is refused, also inside tmux or screen. SSH stays open on sshd's real ports and from the address you ran setup from (never port 2222, which stays tailnet-only) (S3). setup.sh no longer pipes install scripts into a shell: Tailscale 1.102.3 and Docker come from their signed apt repositories with sha256-pinned keys, Ollama 0.33.3 from its release tarball checked against a pinned sha256 (S10). Windows: the folders the SYSTEM wake-watch task runs from are created already locked (explicit ACLs). A folder or file already there is refused if it is a link, has a foreign owner, or has any entry letting another account write it, delete it or change its permissions or owner. This is checked top down before anything is locked, because locking would erase inherited grants, and the refusal says to move the folder away, since removing the access would not undo a change. The wrapper and script are rewritten from the kit on every run, Python runs with -I, and every file in the machine-wide Python folder is checked. An alert.cmd that another account could have changed is set aside, never run, and replaced (S2, round 2); `.env` and `alert.cmd` are readable only by SYSTEM and administrators (and you, for `.env`) (S2). heimdall `deploy.sh` validates `--image`, `--internal-port` and `--health`, writes `.env` values as data and no longer builds a `sh -c` string from the folder path (S6); `backup.sh` and `backup-push` pass the wake host to their port probe as arguments. macOS: no root job runs code from Homebrew or another path your account can change. Tailscale is the signed standalone app, and a re-run retires the root homebrew.mxcl.tailscale service an earlier run started (unless that run arrives over Tailscale, which would cut it off; it then says to re-run from the home network). wake-watch's LaunchDaemon runs as you with /usr/bin/python3 -I (state /var/lib/wake-watch, log /var/log/wake-watch). alert.conf gets a read ACL entry for you instead of `sudo alert` (R2-2). Check: `pwsh -NoProfile -File servers/windows/test_setup.ps1`, `python3 servers/macos/test_setup.py`.
- **Firewall trial (R2-1):** trial, end-of-run re-arm, `--confirm-firewall` and the rollback script share one lock (`/run/homeserver-fw.lock`, moved in R3-1) and each re-checks the trial after taking it. A rollback that loses to a confirm leaves nftables alone and never deletes the table when its snapshot is gone. A confirm that loses to the rollback says 'too late' and exits 1. Check: `servers/linux/test_setup.sh` section 8 E-G.
- **Firewall lock (R3-1):** the lock shared by the trial, re-arm, `--confirm-firewall` and the rollback moved from `/run/homeserver-fw.lock` to `/run/homeserver-fw/lock`. Any account could open the old file and hold it (flock needs no write access), which stalled the rollback. The new lock sits in a root-owned mode-700 folder that setup.sh and the rollback script create with umask 077 and check (owner, mode, not a symlink) before each use. The first run after the update retires the old lock. It waits up to 30 s for an older setup.sh holding it. It stops while a trial of the older version still waits (confirm it with that version, or let it roll back) or while an older setup.sh has the old lock open. Then it puts a root-only folder at the old path. Check: `servers/linux/test_setup.sh` section 8 A, E-H (an unprivileged account probes the lock throughout), L, M1-M4.
- **Firewall confirm (R3-4):** `--confirm-firewall` writes the rules file and boot setting, then reloads the running firewall (`ExecReload`, one `nft -f` transaction) or starts it when it is not running. It no longer restarts it: the restart's stop deleted the table, leaving the box unfiltered until the start, and for good when the start failed. The rollback is cancelled only after both steps succeed. On failure the rules file and boot setting go back, the rules on trial stay loaded, the rollback stays armed and the confirm exits 1. Check: section 8 F (paused just before the load) and H (injected load failure, with the service running and not).
- **Ollama on thor (R3-2):** Ollama still listens on 0.0.0.0, but port 11434 is kept to loopback and `tailscale0` by its own nftables table (`homeserver-ollama-guard.service`, table `inet homeserver_ollama`), never by the firewall on trial. That firewall rolls back to whatever was there before (nothing on a new box) and is not loaded after a restart during a trial. Ollama's drop-in binds it to the guard (`BindsTo=` + `After=`), so Ollama does not run without the table, at boot included. A LAN host that routes the box's tailnet address over the LAN is dropped too; binding Ollama to the tailnet address would not have stopped it. Check: section 8 O, also the re-run and the upgrade from an older drop-in.
- **Windows (S2, round 3):** your own account no longer counts as trusted for what SYSTEM runs. `C:\homeserver`, its tools, `wake-watch.cmd`, `alert.cmd`, `ProgramData\wake-watch` and every file in the machine-wide Python are refused if your account owns them or may write, append, delete, or change their permissions or owner, because anything you run without elevation could plant code there for SYSTEM. Only the Compose folder, its files and `.env` (which Docker Desktop uses as you) still trust you. A refused Python is never patched: delete what the uninstaller leaves and reinstall it for all users. When the Python or the state folder is refused, an existing `wake-watch.cmd` is replaced by one that runs nothing until a run passes.
- **macOS (R3-3):** setup.sh retires Homebrew's root tailscaled only when it can tell how you are connected. It leaves the service running, says why and asks for a re-run from a new ssh session from another computer on the home network, or a terminal at the Mac, outside tmux and screen, in these cases: inside tmux, screen, zellij, herdr, dtach or abduco (environment, TERM screen*/tmux*, or the program above the shell); with an SSH_CONNECTION no live sshd backs or one that comes from the Mac itself (loopback or its own address); with none while the screen is not yours or the shell runs under sshd; or while an ssh or Screen Sharing connection from a Tailscale address is open. Check: `pwsh -NoProfile -File servers/windows/test_setup.ps1` (77 checks), `python3 servers/macos/test_setup.py` (36 checks).
- **Windows (S2, round 4):** wake-watch's wrapper starts the machine-wide Python with `-I -S`. Without site initialization, a `.pth` file in its protected site-packages can no longer add a folder outside the checked tree (such as an editable install pointing at your own project folder) or run an import line, and no `sitecustomize` runs. The wrapper also clears PYTHONHOME, PYTHONPATH, PYTHONEXECUTABLE and `__PYVENV_LAUNCHER__`; Python's path setup reads the last two even with `-I`. setup.ps1 refuses a Python with a `._pth` file beside python.exe or its DLL (it replaces the search path, and its `import site` line turns site back on), a `pyvenv.cfg` beside python.exe or one folder up (its `home` moves the standard library elsewhere), or a folder above it that another account may add files to. It also refuses a Python older than 3.13.15 (python313.dll's file version), which takes itself for a source build when `..\..\Modules\Setup.local` exists, `C:\Modules\Setup.local` for `C:\Program Files\Python313`, a file any account may create, and then loads its standard library from `C:\Lib`, `-I -S` or not (CVE-2026-12003); upgrade it with `winget upgrade --id Python.Python.3.13 --exact --scope machine`. The refusal turns wake-watch off like the others, and every earlier ACL check stays. Check: `pwsh -NoProfile -File servers/windows/test_setup.ps1` (95 checks with a python3 present: real CPython runs the review's `.pth` import line, the module from the outside folder and its sitecustomize under `-I`, and none of them under `-I -S`).
- **macOS Ollama (R4-1):** the thor lane loads its pf rule before it writes or starts the Ollama LaunchAgent that listens on 0.0.0.0, and stops without starting Ollama when installing or loading the rule fails. An agent an earlier run left, which did not wait for the rule, is stopped and set aside first. At every boot the pf LaunchDaemon (macOS programs and root-owned paths only) loads the rule and only then writes that boot's `kern.bootsessionuuid` to `/var/run/org.homeserver.pf.ready`; a failed load removes it. The agent runs, as you, a short wait for that record before it starts Ollama, so after a restart nothing listens on every interface before the rule is loaded, or at all when loading fails; a record from an earlier boot never counts. A re-run whose load fails stops a running agent; a re-run over ssh with nobody logged in at the screen leaves the agent to the next login. Check: `python3 servers/macos/test_setup.py` (47 checks).
- **Windows (S2 and R5-1, round 5):** setup.ps1 also refuses a Python with a `pybuilddir.txt` beside python.exe, empty or not: 3.13.15 and later still take that for a source build and load the standard library from `..\..\Lib`, `C:\Lib` for `C:\Program Files\Python313`. It refuses one with none of `Lib\os.py`, `Lib\os.pyc` and `python313.zip` too, since Python then searches the folders above for `Lib\os.py`, up to `C:\Lib`. With the `._pth`, `pyvenv.cfg` and version checks, that covers every file the path setup of CPython 3.13 and 3.14 (`Modules\getpath.py`) reads beside or above python.exe. ProgramData and Program Files now come from Windows' known-folder API, never from `$env:ProgramData` or `$env:ProgramFiles`, and must be on Windows' own drive (another letter may be a mapped share or a removable disk, whose permissions prove nothing): a persistent per-user value replaces those even in an elevated shell, so `C:\Users\you\pd&whoami&rem` put SYSTEM's state in your folder and ran `whoami` from `wake-watch.cmd`. setup.ps1 reads no environment variable now. " ^ & | < >` or a line break. Each refusal turns wake-watch off like the others. Check: `pwsh -NoProfile -File servers/windows/test_setup.ps1` (179 checks with a python3 present).
